# 科大云宇宙双端开发计划

讨论稿 · 2026-11-18 · 代码基线 `lusir11/ustc-cloud-universe@0072230`

**首个可验收目标**是让一名新生在 Windows 和一部真实手机上完成同一次游览：从老北门出发，沿路辨认地标，到达图书馆，进入一个公共空间，再回到校园。两端共用地点、米制坐标和交互规则，分别适配输入、画面和加载。第一轮以 Windows 和 Android 原生包为建议测试组合，iPhone 的支持范围及测试设备由团队决定。网页另作免安装路演入口。

新版已包含图书馆游览记录、教学楼室内、Web 专用入口和触控测试。工程当前列出 Windows Desktop、Web Streamed 两个导出预设。触控测试脚本明确只加载玩家与输入，不加载校园模型。手机原生包、完整路线和持续帧率需要真机验证。工作从已有图书馆入手，可以同时观察建筑近景、室外到室内的加载和两端操作。

## 1. 零基础怎样用几天学会第一件资产

建议安排四天，每天约两小时。选一张校园长椅当贯穿案例。先记录座高、总长及侧面照片，保留一份原始模型，后续每天都能看到昨日工作的效果。

| 天 | 学什么 | 当天交付与自检 |
|---|---|---|
| 第一天 | 视图旋转、平移、聚焦，物体模式，米制尺寸，移动、旋转、缩放 | 用长方体搭座板、靠背和椅腿。量一次座高，放到现有学生模型旁看比例 |
| 第二天 | 编辑模式的点、边、面，挤出、倒角、镜像、阵列，原点和应用缩放 | 做圆润的板边与重复椅条。改一次椅条间距，确认模型仍可编辑，四脚落在同一平面 |
| 第三天 | 材质槽、粗糙度、UV、法线、导出选中对象到 GLB | 让木板和金属各用一套共享材质。在 Godot 小场景看正反面、比例、颜色和朝向 |
| 第四天 | 在当前校园实例化模型，设置碰撞，拍同机位截图，提交源文件与运行资产 | 玩家绕椅子走一圈。队友拿到 .blend、GLB、位置和导出说明，能独立复现。下一件做一组可复用窗框 |

常用操作：中键旋转，Shift＋中键平移，小键盘句点聚焦，Tab 切换编辑模式，G/R/S 移动、旋转、缩放，N 面板读尺寸。Godot 中 Y 向上，项目以米为单位。独立长椅可把原点放在地面接触中心，整栋楼先查生成器有没有把校园坐标写入顶点。入门可查 [Blender 官方手册](https://docs.blender.org/manual/en/latest/)。

## 2. PC 和手机双端该选哪种引擎

| 决策项 | Godot 4 | Unity 6 | Unreal Engine 5 |
|---|---|---|---|
| 与现有团队的衔接 | 现有玩家、NPC、碰撞、场景构建、检查工具均可继续用。你能集中练建模与材质 | Blender 资产和地理数据可迁移。用 C# 重写区域装配、玩家、交互、联机接线与测试 | 资产和数据可迁移。用 Blueprint 或 C++ 重做项目逻辑，重新配置材质、碰撞、输入与打包 |
| PC 画面 | Forward+ 适合现有桌面版的校园光照和水面 | URP 可以覆盖风格化桌面校园并共享移动资产。HDRP 适合优先追求高端桌面画质的项目，另养一套管线会增加成本 | 精细地标、复杂光照和宣传演出值得评估，材质编辑及场景制作工具强。编辑、着色器编译与打包也占用开发时间 |
| 手机画面 | 优先测试 Mobile，旧设备可评估 Compatibility。更换渲染器后复看水、树叶、阴影和自定义着色器 | URP 的渲染比例、光源、阴影和每档管线资源便于按机型分档。现有 Godot 的着色器需重新做 | 有专用移动渲染路径和设备配置。普通手机应从烘焙照明、简化材质和有限动态灯开始，Nanite、Lumen 按设备及支持矩阵评估 |
| 代码和工具 | GDScript 与场景树学习路径短。团队要自己维护部分编辑和性能工具 | C#、Profiler、Frame Debugger 与移动工具链适合多人协作。插件版本和平台差异也需要维护 | Blueprint 有利于快速试交互，C++ 可控制底层行为。Unreal Insights 适合复杂性能诊断，团队学习面最大 |
| 成本 | MIT 许可，无引擎版税，分发保留许可说明 | Personal 有资格门槛，按团队与业务适用条件核算席位；插件另计 | 游戏适用许可通常涉及单产品累计收入门槛及版税，例外和优惠按发布协议核算 |
| 适合本项目的条件 | 首选。用较小代价验证双端、风格和制作人效 | 若目标手机上的实测与团队已有 C# 能力能抵回迁移成本，值得做一次限时对照 | 若高端 PC 画面成为首要卖点，且有人能长期维护移动材质、构建与性能，可进入候选 |

**选型办法**：先用 Godot 做一条可走通的双端路线。记录 Android 真机最低表现、触控问题、完成一件资产的工时和包体。如果瓶颈明确且在预算内难以解决，再把同一段路、同一组模型、同一摄像机带到候选引擎。三者都能展示漂亮画面，决定取舍的是达到同一交付标准所需的设备、人员和时间。

**手机端还多出一层交互工作**：左侧移动、右侧拖动视角，独立交互按钮，面板打开时停止转镜头，处理异形屏安全区、系统返回、前后台恢复。NPC 问答服务要从真机访问可达地址，并验证弱网时仍能游览。若纳入 iOS，排期中加入 Mac、Xcode、签名和真机验证。Web 入口则另测浏览器内存、首次下载、缓存与触控。

依据：[Godot 渲染器](https://docs.godotengine.org/en/stable/tutorials/rendering/renderers.html) · [Godot 许可](https://godotengine.org/license/) · [Unity URP](https://docs.unity3d.com/6000.0/Documentation/Manual/universal-render-pipeline.html) · [Unity Personal](https://unity.com/products/unity-personal) · [UE 移动开发](https://dev.epicgames.com/documentation/unreal-engine/unreal-engine-creating-mobile-games) · [UE 许可](https://www.unrealengine.com/en-US/license)。

Android 首包在 Godot 配好 OpenJDK 17、Android SDK 和匹配引擎版本的导出模板，新增 Android 预设，先把调试 APK 安装到目标手机。测完室外与室内切换，再做签名发布包。iOS 需要配好 macOS、Xcode 和签名。两端都要记录实际设备和系统版本。[Godot Android 导出](https://docs.godotengine.org/en/stable/tutorials/export/exporting_for_android.html) · [Godot iOS 导出](https://docs.godotengine.org/en/stable/tutorials/export/exporting_for_ios.html)。

## 3. Atlas 和 Meshy 放在哪一步能省时间

**Atlas 用来研究一个空间。** 这里按 World Labs 的 Atlas 评估。Viewfinder 可以从照片重建场景并预览镜头，Chisel 用灰模控制空间结构，Splats to Mesh 可将点状渲染表示转换成有几何表面的网格。选校内一处有柱廊的入口，用有权上传的照片试做。用门宽和两处柱距作标尺，核对柱子是否笔直、背面是否完整、相邻视角是否一致。通过的结果可做构图参考或环境草稿，正式楼体仍用校园布局定位，在 Blender 整理可编辑部分并单做碰撞。[Atlas 官方说明](https://worldlabs.ai/atlas)

**Meshy 用来试做单件道具。** 选石凳、花盆或雕塑底座，拍同一物体的正面、侧面、背面，保持光线一致，清理背景。先看生成的几何，再选贴图和重网格化，导出 GLB 到 Blender。校正尺寸、原点、法线、材质数，补上底面和简单碰撞，最后在手机上看轮廓与贴图。规则窗框、栏杆、整齐排列的椅条优先用阵列或参数化脚本，后续改尺寸更省力。[Meshy 图生 3D](https://docs.meshy.ai/en/webapp/image-to-3d) · [多视图指南](https://help.meshy.ai/en/articles/12634481-how-to-use-multi-view) · [套餐与输出许可](https://docs.meshy.ai/en/webapp/pricing)

**做一轮对照实验。** 相同照片、相同用途，各做一件手工道具和 AI 辅助道具。记录采集、生成等待、人工修模、贴图、引擎返工、积分费用，以及最后手机帧耗时。按“通过验收的一件资产”计算人工分钟数与总费用。若生成很快但两次改尺寸都要重做，就把它用于概念或背景资产。每件保留来源、工具版本、生成参数、许可和人工修改记录。涉及真人面孔、室内信息或第三方图像时先确认上传权限。

## 4. 何时定画风，已有模型怎么改

用同一段“红砖建筑＋树荫＋水岸＋人物”做三种小样：简洁的低多边形、接近校园实景的风格化材质、沿用项目历史的印象派光色。固定镜头、时间、地理布局，分别看一张人高图、一张建筑近景、一段转动镜头的手机录像。让熟悉校园的人辨认地点，让新玩家找到入口，建模成员记录生产耗时。共同评审辨识度、风格统一、移动中是否闪烁、手机性能和批量修改成本。

选定后形成一页美术规范，写明色板、建筑倒角、窗格细节、树冠轮廓、纹理密度、人物比例和两档光照。**全部资产都按新规范复核，按差异决定修改量**：共用材质即可统一的先改材质，轮廓或比例不符的改几何，近景地标单独精修，远景保留简化版本。按区域分批迁移，每批留同机位前后对照，保证已有通行路线。

## 5. 正式发布前如何优化

暂定 PC 1080p／60 FPS（每帧约 16.7 ms），中档 Android 30 FPS（约 33.3 ms）。等团队给出最低目标机型后锁定画质、分辨率与阈值。第一周就记录基线，发布前再做完整回归。

| 观察到的问题 | 优先定位 | 可试路线和验证方法 |
|---|---|---|
| 湖边、树荫转镜头掉帧 | 对比 GPU 帧时间，单独调整倒影、阴影、渲染比例 | 手机降低或替换平面倒影，缩短阴影距离，降低透明叶片重叠；同机位检查树冠与水面仍可辨识 |
| 远景建筑和植被开销高 | 统计提交图元、材质、可见批次 | 复用现有 LOD 和空间 MultiMesh，远处楼群试 HLOD，建筑密集区测遮挡剔除；走近时检查跳变 |
| 初次启动慢、跨区卡顿或内存过高 | 记录冷启动、加载峰值、跨区帧时间与内存 | PC/手机分别定纹理尺寸与压缩格式，按相邻区域预加载、卸载远区；连续往返看内存是否回落，保留路面和人物状态 |
| 人多时 CPU 忙 | 比较脚本、物理、动画耗时 | 简化远处角色更新频率、复用材质与动画、按用途设置碰撞；检查接近 NPC 时交互和动画及时恢复 |
| 手机运行十分钟后变慢 | 固定亮度、设备、画质，热机重复路线 | 看 P95 帧时间、峰值内存、发热、前后台恢复；必要时限制帧率，提供低档画质并重新跑相同路线 |

发布候选版在最低目标机和代表性 PC 上分别跑冷启动、10–15 分钟连续步行、图书馆进出、NPC 交互、弱网恢复和多次跨区。每轮比较同条件的平均与 P95 帧时间、长卡顿次数、加载秒数、峰值内存和包体。历史桌面短测单独存档。

## 7. 第一次团队计划会要定哪些事

| 顺序 | 时间建议 | 决定或交付 |
|---|---|---|
| 起步 | 第 1 天 | 指定目标 PC、一台中档 Android 和最低支持设备；确定 iPhone 是首发还是后续。选定图书馆样段和对比机位 |
| 学习与首包 | 第 1–4 天并行 | 你完成长椅练习，负责引擎的成员从新版导出并在真机跑通首包，记录第一份性能数据 |
| 风格与 AI 小试 | 第 5–7 天 | 三个画风小样、Atlas 空间试验、Meshy 道具与手工对照。选一种画风并签入资产规范 |
| 双端样板 | 第 2 周 | 两端完成同一条路线；交付一组可复用模型、双端实机录像、性能表及返工清单。依据数据决定保留 Godot 或启动候选引擎对照 |
| 扩展至发布 | 样板验收后排期 | 按区迁移美术，逐区回归通行与性能，最后做长时间、多设备、安装更新与网络测试 |

你负责资产与生产工时，引擎成员负责双端首包及测量，熟悉校园的人负责地标辨识评审。团队当前最值得先定的三个参数是最低手机型号、首发操作系统和一段能在两分钟内走完的演示路线。
